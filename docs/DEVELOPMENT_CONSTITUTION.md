# 临期宝开发宪法与单人工作流

本项目由项目 owner 一人开发。项目 owner 是产品决策者、任务排序者和最终合并者；Codex 按 owner 当前授权的任务提供实现、解释和审查协助。默认不与其他开发者或代理并行开发。Workbuddy 不属于常规流程，只有 owner 明确要求时才用于独立评审或建议。

产品行为以 `docs/PRD.md` 为准；架构以 `docs/TECHSTACK.md` 为准；数据库以 `docs/DATABASE.md` 和 migrations 为准。文档冲突时，先由 owner 决定并更新文档，再改实现。

## 1. 产品不变量

1. 正式交付物是可安装的 iOS / Android App；HTML 仅作交互原型。
2. `rows × columns` 是容器正视图格数；每格纵深容量独立。3×2×5 是六格 A–F、每格五件。
3. 一件实物对应一条在库记录。条码不是商品主键，也不能假设唯一。
4. 过期日等于生产日期加预计存储天数；生产日期当天为第 0 天，临期状态按门店时区和门店统一阈值动态计算。
5. 移除必须先选中单件，再核对完整条码。验证失败绝不修改库存。
6. 下架后同格后续商品前移；位置由格子和深度序号计算，不能把展示编号当永久商品 ID。
7. 库存操作、审计事件和位置重排要么全部成功，要么全部失败。

## 2. 文档是唯一共享上下文

产品和技术规则必须落在仓库文件中，不依赖个人聊天记录、口头约定或某一次 Codex prompt。每个任务开始时读取 `AGENTS.md` 和相关文档。

- `docs/PRD.md`：用户流程、业务规则、范围和验收标准。
- `docs/ROADMAP.md`：Phase、Task、依赖和顺序。
- `docs/TECHSTACK.md`：架构、依赖和环境约定。
- `docs/DATABASE.md` + `supabase/migrations/`：数据模型与真实 schema。
- `docs/DEVELOPMENT_CONSTITUTION.md`：永久约束和单人开发流程。
- `docs/DECISION_LOG.md`：已确认的产品/架构决定、理由和影响。
- `AGENTS.md`：Codex 仓库级工作约定。
- GitHub Issue：当前单一任务及其验收清单；PR 描述留存改动与验证记录。

文档更新与依赖它的代码在同一个变更中完成。Owner 在聊天中确认但尚未写入文档的决定，不能视为已记录的长期规则。

## 3. 单人 GitHub 工作流

- 使用一个私有 GitHub 仓库作为版本历史和备份；`main` 保持可构建状态。
- 每次只推进一个当前任务。先创建/更新 Issue，写明目标、验收标准、涉及模块和依赖。Issue 是任务范围与验收记录的来源。
- **单人开发直接在 `main` 上提交**（owner 2026-10-23 决定，见 ADR-007）：不为每个任务开 `feat/*`、`fix/*` 短期分支，PR 不是完成任务的必经流程。
- 需要额外留档、回滚点或集中自查时，可临时建分支并发 PR，由 owner 自行决定；这属于可选动作，不是流程前置条件。
- 即使直推 `main`，提交前仍要集中检查 diff、文档、运行结果和未完成项；重要节点建议打 tag 便于回滚。
- 分支保护：当前私有仓库使用 GitHub Free 计划，branch protection API 返回 403（"Upgrade to GitHub Pro or make this repository public"），**无法启用**。单人流程不依赖强制保护，改用提交前自查与「`main` 始终可构建」保证。若将来多人协作或升级计划，重新评估并 supersede ADR-007。
- Workbuddy 不直接提交或并行实现；若 owner 明确要求评审，提供的建议仍由 owner 判断和落地。
- 不提交 `.env`、密钥、真实门店导出、用户数据、构建产物或未授权图片。
- 依赖锁文件必须提交；迁移文件按顺序命名且不可修改已部署的 migration，修正要追加新 migration。

## 4. 每个任务的固定节奏

1. **选任务**：从 Roadmap 选择当前唯一 Task，确认它的前置条件已经满足。
2. **定完成条件**：把可观察的验收标准写进 GitHub Issue；若需求不清楚，先更新 PRD/ADR。
3. **实施**：Codex 只围绕当前任务修改必要文件，不扩张范围、不启动子代理、不同时改下一项任务。
4. **检查**：检查 diff、业务边界、错误/空/加载状态、权限、文档和数据库一致性；只报告真实运行过的验证。
5. **收尾**：更新 Issue/文档，提交变更（直推 `main` 或经可选 PR 合并），记录风险与未完成项，再开始下一项。

每个任务收尾必须说明：关联 Issue、用户可见变化、验收结果、实际验证命令和结果、数据库迁移/RLS 影响、截图（若涉及 UI）、风险与后续工作。这些内容写在 Issue 评论或 PR 描述中均可。

## 5. 数据、安全和隐私

- 所有门店数据按 store membership 做服务端授权；隐藏 UI 不等于授权。
- 不收集不需要的员工/顾客信息；日志禁止输出完整条码、认证 token 或原始包装照片。
- 图片上传 OCR 需先由 owner 确认用途、服务商、留存期和隐私告知后再实现。
- 权限最小化；相机只在用户进入扫描时申请；拒绝后仍可手动录入。
- 生产数据修改需有备份和明确恢复方案；不把本地 seed 或原型数据混入生产环境。

## 6. 变更与规则例外

- 影响用户流程或数据库的决定写入 `docs/DECISION_LOG.md`，并同步更新 PRD/Techstack/Database。
- 技术版本在 lockfile 中锁定；文档说明原则，不把 `latest` 当作可复现版本。
- 如需偏离本宪法，先在 Issue/ADR 写明原因、范围、风险和恢复方式，由 owner 决定后实施。
