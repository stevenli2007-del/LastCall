# Roadmap

路线图按依赖拆分。每个 Task 在 GitHub 中建立 Issue，完成定义写在 Issue 中。Phase 顺序可根据试点反馈调整；本路线图不承诺具体日期。

## Phase 0 · 产品与工程基线

- **T0.1** 冻结 MVP 术语和规则：生产日期、预计存储天数、过期日、临期阈值、A1 位置规则。
- **T0.2** 初始化 GitHub 仓库、Issue/PR 模板和提交流程。单人开发直接提交 `main`；私有仓库 Free 计划不支持分支保护（ADR-007）。
- **T0.3** 初始化 Expo React Native TypeScript 工程、环境配置和 iOS 开发构建；验收时从干净 checkout 执行 `npm ci`，并在 iOS Simulator 启动开发版。Android 暂缓（ADR-008）。
- **T0.4** 建立 Supabase local dev、迁移目录、生成类型流程和本地 seed 数据。
- **T0.5** 把现有 HTML 原型作为交互参考，建立移动端设计 token 和屏幕清单。

**完成条件：** 项目 owner 可从干净 checkout 启动 App 和本地后端；文档及 schema 有唯一版本来源。

## Phase 1 · App 骨架、账号和门店权限

- **T1.1** 建立底部导航：首页、Add、Remove、Sell（占位）、Settings。
- **T1.2** 登录、退出、恢复会话和未登录路由保护。
- **T1.3** 门店成员与角色（owner/manager/staff），配置 RLS。
- **T1.4** 建立统一加载、空状态、错误提示、相机权限拒绝和手动输入 UI 规范。
- **T1.5** CI 基础：静态检查、类型检查、构建检查；PR 必须绿灯。

**完成条件：** 登录用户进入自己的门店，跨门店访问被 RLS 拒绝；iOS 能构建开发包。Android 构建暂缓（ADR-008）。

## Phase 2 · 容器与 Add 上架

- **T2.1** 容器创建表单：名称、冰柜/货架、行、列、纵深容量。
- **T2.2** 生成正视图格子 A–Z/AA…；布局只按行列展示。
- **T2.3** 格位选择和逐件上架流程；支持不填满格位。
- **T2.4** 条码相机扫描（含支持的零售条码格式）与手动输入 fallback。
- **T2.5** 生产日期手动输入和日期扫描入口；确认前允许校正。
- **T2.6** 上一件预计存储天数作为下一件默认值；自动预览过期日期。
- **T2.7** 保存后刷新格位容量、单件位置和首页库存摘要。

**完成条件：** 按 PRD 验收标准完成 3×2×5 添加流程；条码重复与日期独立；数据库并发写入不产生重复格位深度。

## Phase 3 · 首页提醒与 Remove 下架

- **T3.1** Store timezone 和临期天数配置；数据库视图/RPC 统一计算本地状态。
- **T3.2** 首页显示临期和过期项；点击跳转到容器及格位。
- **T3.3** Remove 列表支持选择具体单件商品。
- **T3.4** 扫码核对完整条码，匹配失败不变更数据。
- **T3.5** 数据库事务/RPC：记下架事件、移除库存、同格紧凑重排。
- **T3.6** 验证相同条码多件商品按用户选中的位置移除。

**完成条件：** 到期日、状态和位置一致；移除与历史记录原子提交；没有“只从 UI 隐藏”的假删除。

## Phase 4 · 门店试点与上线准备

- **T4.1** iOS TestFlight 发布流程、版本号与回滚说明；Android 内测暂缓（ADR-008）。
- **T4.2** 真实 iPhone 验证相机权限、焦距、条码读取率和弱光情况。
- **T4.3** 弱网、超时、重复点击、离线只读和服务端冲突 UX。
- **T4.4** 数据备份/恢复演练、错误监控、隐私说明和账号删除/门店停用流程。
- **T4.5** 门店试点反馈整理，确定 v1 上线门槛。

**完成条件：** 试点人员可完成日常上架与下架；关键业务问题可追踪；数据能按既定策略备份恢复。

## Phase 5 · 反馈驱动扩展（MVP 之外）

- **T5.1** 离线写入与同步队列（先定义冲突和幂等策略，再实现）。
- **T5.2** OCR 日期识别评估：置信度、人工校正、隐私和成本评估。
- **T5.3** Sell/售卖、POS 对接或手动售出流程。
- **T5.4** 多门店、库存报表、盘点和推送通知。

## 单人实施节奏

- 项目 owner 是唯一实现协调者和产品决策者；Codex 一次协助一个任务，不启动并行代理或同时推进多个功能分支。
- 每次只选一个当前 Task：先完成所需文档和接口，再实现一个完整可见的用户流程，完成验证并合并后，才开始下一个 Task。
- 按 Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 顺序推进。Phase 2 先完成容器与 Add 的端到端闭环，再进入 Phase 3 的提醒和 Remove。
- GitHub Issue 记录当前任务与验收标准；单人开发直接提交到 `main`，feature branch/PR 仅作可选留痕（ADR-007）。不要求第二位审批者；Codex 可协助做审查清单，但 owner 决定是否合并与是否推送。
- Workbuddy 不属于常规开发流程。只有 owner 明确选择时，才用于独立评审或一次性建议；不承担并行实现，也不成为任务完成的前置条件。
